# 2026-10-31 写章篇幅与引文可靠性复验

接续 `2026-10-31-live-workflows.md`。当前主代理独立实施，使用既有 Gemini Chat 配置和独立测试作品；没有改动原有小说，也没有降低字数、引文或自动采用检查。

## 最终实现

1. **写章的 C5 从原文目录选择引文编号。** 程序按连续原句生成本次正文的目录，结构化 schema 提供可选编号，模型用 `@quote:N` 指定出处。程序在解析结构前将编号还原为原文；未知编号报错。正文与模型摘要之间仍需语义核对，出处在正文里不等于摘要必然正确。旧客户端逐字返回 quote 的响应仍可读，但必须过原来的锚点检查。两条写章路径（产品任务与独立章循环工装）同步接线；旧稿反推只共用改进后的引用说明，本轮未改其输出协议。
2. **纯短稿的唯一一轮自动修订改为插入补写。** 原稿与最后一段保持逐字不变；仅生成章末前的新增正文。新增字数目标从原预算 sweet 减去实测字数派生，不加经验倍率。正常补写直接返回正文；需要扩大范围时保留 expand_scope 分支。空输出、整章重复、不完整响应仍拒绝应用。模型在新增内容尾部重复固定结尾时，只剥掉那一份逐字重复，最后仍拼接原稿的结尾。
3. **额度未增加。** 仍只创建一份自动候选、进行一次补写，之后用新全文重新声明与检查。混有未收伏笔等正文缺项时仍走原整章修订；引文不匹配等非正文问题仍不靠重写正文来迎合。

## 验证与剩余边界

回归覆盖：原文编号还原、未知编号 fail closed、旧引文兼容、草稿中不残留编号；原稿前缀及结尾不变、空补写/整章重复拒绝、固定结尾去重、暂停/恢复、expand_scope、一轮修订上限及只用合成后全文检查。

`npm test`：80 文件，1382 passed / 1 skipped；`npm run typecheck`、`npm run web:build`、`git diff --check` 通过。构建仍有大 chunk 提示。本轮没有浏览器验收，也没有完成人工文学质量评审。

剩余问题是**一次补写仍不能稳定达到目标**，并且可能超长。现有上限用尽后必须保留结果等待作者，不能继续隐藏调用、截断正文或放宽闸门。若后续要追求稳定自动连写，需要另行设计有总次数/积分预算、可暂停恢复的分场生成，而不是无限重试当前整章接口。
