# novel-forge 用户流程与现有能力映射

日期：2026-09-09

状态：设计补充草案。依据同日的[首版用户流程设计](2026-09-09-novel-forge-user-flow-design.md)和本次静态源码复核，说明哪些能力可以复用、哪些需要接通，以及建议的开发顺序。默认创作节奏和首版范围仍待用户评审；本文不是已批准的实现计划，也不代表运行验收完成。

## 1. 作者实际要走通的主线

提出想法 → 确定开篇方向 → 写出一章 → 看摘要、结构变化和正文 → 修改或采用 → 继续下一章 → 返回接着写 → 导出已采用正文。

作者可以随时通过对话插入查询、讨论和修改。主 Agent 根据意图选择工具；进入写章任务后，由章节流程协调准备、正文、结构声明和检查。作者主要在创作方向和结果采用上作决定。

现有项目已经具备章节生成、规则检查、结构事件、落盘和阅读视图的基础。当前应优先把这些基础接成可持续使用的创作流程。

## 2. 每一步对应哪些能力

| 作者的操作 | 应交付的结果 | 当前可复用的代码 | 仍需补齐的连接 |
| --- | --- | --- | --- |
| 新建一本书，描述想法 | 保存作品和作者明确指定的内容，分开显示 Agent 的建议 | `src/types/work.ts`、`src/types/character.ts`、`src/store/persist.ts` | 作品创建和选择入口、对话式补充资料、建议的保存与采用；现有存储结构不等于已有建书体验 |

| 说“采用这个版本” | 正文、依赖设定和结构变化共同成为正式创作依据 | `src/store/event-stream.ts`、`src/store/project.ts`、`src/store/persist.ts` | 按稿件版本采用、采用前条件核对、重复请求保护、一致保存和过时版本处理 |
| 说“采用并继续”，或隔天回来 | 使用已采用内容续写；返回时看清待处理稿和未完成任务 | 项目加载、事件恢复、概览及上下文模块 | 采用与续写的衔接、对话和任务恢复、避免重复生成；离开页面后在既定范围内继续并重新连接同一任务；采用成功后续写失败只恢复后者 |

“可复用”仅指源码中存在对应基础。上表没有把某个模块存在当成完整用户能力已经实现。

## 3. 当前代码中需要先处理的三个衔接点

### 3.1 生成正文后就要保留成果

`src/chapter/pipeline.ts` 的 `ChapterRunResult` 在失败时仅返回步骤、错误和指标。C4 生成正文后，C5 调用失败、被拒或返回非法 JSON 的分支没有把正文带回；当前函数本身也未把它保存为可恢复草稿。

因此，仅给 `runChapter` 增加一个网页调用入口，还不能满足“正文写好了，检查失败也不丢稿”。需要在正文步骤完成后保存产物及恢复所需的上下文，再执行后续步骤。C5 继续保留完整 C4 响应的既有约定也要纳入恢复设计，不能只保存提取出的纯文本。

可验收结果：故意让结构声明失败后，作者仍能查看正文；重试从声明开始，不再次执行正文生成。

### 3.2 采用必须精确到稿件版本

`src/store/event-stream.ts` 的 `decideChapter` 按章号处理该章全部 proposed 事件。若直接用它承接同章多个草稿，缺少只采用其中一版的选择边界。`src/store/persist.ts` 当前以 `chapters/ch{n}.txt` 保存正文，同样不能单独表达草稿历史与某版正式正文之间的关系。

后续需要让正文、声明、检查和依赖的作品版本指向同一份稿件。采用时只生效用户选中的版本；修改最新已采用章时，还要让后续投影和上下文使用替换后的有效版本，避免旧、新结构事实一起生效。小说事件流继续承担故事事实记录，任务进度另行保存。

可验收结果：第一章有初稿 A 和修订稿 B 时，采用 B 只影响 B 对应的事实；重复采用 B 不重复写入；基于旧作品版本的稿件先重新核对。

### 3.3 对话需要真正执行工具并读取结果

`src/context/tools.ts` 声明了人物、设定、章节读取和提出修改等工具。当前源码搜索中，`appendTurn` 只有定义，`runChapter` 在 `src/` 内的调用方仍是验收脚本；尚未看到完整的工具调用、执行、结果回传和模型继续判断循环。`src/server/api.ts` 和 `web/src/App.tsx` 目前主要承接阅读、体检、结构视图和告警操作。

需要接通主 Agent 与小说业务能力，并处理写作调用中实际出现的工具请求。主 Agent 理解作者的自然语言后选择工具；工具执行代码校验对象、范围和当前状态，再把结果交回 Agent。按钮操作和对话操作复用相同的业务入口。

可验收结果：作者查询人物信息时只得到有依据的回答；要求写章时真正创建章节任务；工具失败能显示原因并按需要重试；无明确采用意图时不会把草稿变成正式章节。

## 4. 建议的开发顺序

以下是能力的依赖顺序，仍需在范围确定后拆成文件级实现计划。

| 阶段 | 建设重点 | 阶段验收结果 |
| --- | --- | --- |
| 1. 可靠的章节任务基础 | 为现有生成和检查能力补上步骤保存、草稿版本、检查关联及采用边界；保留已有作品数据和事件含义 | 在已准备的作品中生成一章，失败能保留正文，指定版本能被正确采用；重复请求不造成重复正式内容 |
| 2. 作者能通过对话完成首章 | 新建作品与基本资料、规划建议、主 Agent 工具循环、任务 API、对话和章节结果界面 | 从一句想法开始，经选定方向、写章、看结果到采用第一章；按钮与对话得到相同状态 |
| 3. 修改后持续创作 | 自然语言局部修订、手动编辑、结构记录纠错、重新检查、最新已采用章修订及下一章草稿失效处理 | 修订稿采用后，下一章遵循新事实；旧稿事实不再混入；正确正文可保持原样并纠正结构误读；回来能继续未完成步骤 |
| 4. 完整检查作者体验 | 安排与兑现的展示、作品进度与待办、基础正文导出、连续创作验证 | 连续写 3～5 章，作者能看懂结构变化并干预，返回不重复生成，导出内容与所选正式版本一致 |

保存、重复请求和恢复从第一阶段贯穿后续阶段。第 4 阶段负责完整体验验收，不能把这些基础保障推迟到最后才设计。

建议第一项开发任务聚焦“可靠的章节任务基础”：把当前章循环变成可保存、可恢复、可按版本采用的业务能力。随后主 Agent 和网页接入同一个入口。当前仍不需要扩展角色数量、旧作导入或跨多章正式返修。

## 5. 对框架选择的影响

上述能力可以继续复用 TypeScript、Claude SDK 和现有小说模块。LangChain 可用于模型与工具交互，是否引入单独评估；LangGraph JavaScript 可评估用于步骤编排与持久恢复。任何框架都不会自动解决正文版本、作者采用、结构事实一致性或写作质量问题。

选型时应以三个情境验证方案：正文成功而声明失败、等待作者采用后离开再返回、采用成功而下一章生成失败。若评估 LangGraph，其运行检查点与小说正式事实仍应保持各自职责。当前没有选定或安装框架。
