# novel-forge 首版用户流程设计

日期：2026-09-09

最近更新：2026-09-10（当前主代理复核）

状态：评审草案。用户已确认需要通过对话下达任务、由 Agent 自主选择工具，并要求从用户使用角度梳理流程。本文件提出的默认创作节奏、首版范围和操作细节是建议，尚未逐项得到用户确认。

## 1. 目标体验与范围

用户进入一本小说后，能够用自然语言提出创作任务，通过摘要和结构变化判断结果，按需跳到正文核对，修改并采用结果后继续下一章。隔天回来仍能接上作品和未完成任务。

本次细化聚焦一条可验证的主线：新建作品 → 明确基本设定 → 生成一章 → 看结果 → 修改 / 采用 → 下一章 → 返回继续。

对话始终可用，用户可随时讨论、查询、规划、写作或提出修改。各阶段说明用户如何达成目标，不要求用户每次都从头经过一套表单。

完整产品还包含旧作导入、跨多章返修、批量创作、可配置角色和更多导出能力。这些能力属于后续范围；当前首版建议先支持已采用正文的基础文本导出。

本文件约定用户可见行为，不决定 LangChain / LangGraph 选型、模型数量、API 路由或数据库结构。

## 2. 创作节奏的选择

| 方案 | 用户怎样参与 | 收益与代价 |
| --- | --- | --- |
| 逐章采用，首版推荐 | Agent 执行一章的生成和检查，用户看结果后采用或修改 | 可以尽早发现方向和记忆问题；每章需要一次结果判断，可用“采用并继续”衔接 |
| 按阶段集中采用 | 用户给定一个阶段目标，集中审阅多章草稿 | 连续创作更顺畅；需要处理多章草稿之间的依赖和局部返修 |
| 预先授权自动采用 | 用户约定目标、边界和消耗范围，Agent 自动推进正式进度 | 人工操作少；质量判断或结构记录出错时，会影响更长的后续内容 |

以下流程默认采用第一种节奏。用户一句明确的“采用并继续”就能连接两章，无须分别确认内部的准备、生成和检查步骤。

## 3. 用户可访问的内容

| 入口 | 用户能看到什么 | 用户可以做什么 |
| --- | --- | --- |
| 作品列表 | 作品名称、最近进度、未完成任务提示 | 创建、打开作品 |
| 对话 | 当前任务、问题、建议、结果及历史交流 | 下达任务、追问、修改方向、暂停、采用 |
| 作品资料 | 已确定设定、人物、写作偏好、规划和备选想法 | 查询、修改、区分已确定内容与建议 |
| 故事概览与结构视图 | 已发生事件、未来安排、人物变化、伏笔及需要处理的问题 | 查看影响、安排下一步、跳到证据正文 |
| 章节结果与正文 | 草稿、检查结果、具体改动、已采用版本 | 阅读、定位、改写、手动编辑、采用、查看历史 |

对话可以直接发起上述操作，其他入口提供可见的操作按钮。通过按钮和自然语言完成同一操作时，产生相同的作品状态。

打开作品时先回答三个问题：当前写到哪里、有哪些结果等用户处理、接下来可以做什么。运行中的任务显示在同一作品中。

## 4. 首次使用：从想法到第一章

### 4.1 创建作品

用户从作品列表选择新建，可以直接描述想法，例如：“写一本带悬疑感的玄幻小说，主角从寻找失踪的母亲开始。”书名可以暂定。

Agent 整理用户已经指定的内容，并提出影响开篇的必要问题。一次只推进一个关键分歧；主角姓名等细节如果用户授权 Agent 决定，可以作为建议加入本次创作方案。

结果分为“你已指定”和“建议补充”。用户明确给定的信息作为作者设定保存；Agent 补充的内容先作为建议，用户选择或认可后才成为正式设定。

用户明确指示修改某条设定时，直接记录该选择并展示变更。若与已有正文冲突，先保留为修改建议，说明受影响内容，进入第 8 节的修改流程。

### 4.2 形成可开写的方案

Agent 提出核心人物、必要设定、故事阶段方向以及第一章目标。全书方向可以较粗，第一章需要明确人物当前目标、阻力、实际变化和结束位置。

用户可以要求继续讨论，也可以说“就按第二个方向开始写”。这一指令同时认可所指向的方案并启动首章创作；Agent 展示本次采用的设定和目标，不再重复询问同一选择。

当用户只授权“先写一版看看”时，允许基于建议设定产出草稿，但界面和后续查询必须标明它所依赖的设定仍是建议。采用该章时，一并展示并采用这些依赖，不能静默把建议当成已确认事实。

### 4.3 首章完成后

用户看到一份章节结果，格式遵循第 6 节。用户可以讨论、查看原文、修改、采用，或者采用并继续。

正式采用后，第一章正文、用户接受的新设定和对应结构变化一起成为后续创作依据。作品概览显示“已采用第 1 章”，接下来可继续第 2 章。

## 5. 日常使用：不同表达如何触发操作

| 用户表达示例 | Agent 行为 | 对作品的影响 |
| --- | --- | --- |
| “如果师父就是反派，会怎么样？” | 讨论可能性，给出影响和可选方向 | 保存为对话中的建议；用户说“记为备选”后加入备选想法 |
| “主角在第三章时知道这件事吗？” | 按指定章节和版本查找证据，区分正文事实、未来计划及推测 | 不改变正文或设定 |
| “把这条线索安排到下一章” | 修改下一章计划并展示安排 | 计划变化；伏笔仍未兑现 |
| “按已确认计划写下一章” | 准备、生成、检查，并交付待采用稿 | 新增草稿和候选结构变化 |
| “把这一段改成谈判，不改变结局” | 按约定范围修改当前草稿，再检查相关内容 | 新草稿版本，旧版本可查看 |
| “记住，以后台词少用感叹号” | 更新作品写作偏好，说明后续如何应用 | 后续创作使用新偏好；已采用章节保持原版本 |
| “采用这个版本” | 检查版本与采用条件，采用正文及对应变化 | 正式作品进度更新 |
| “采用并继续下一章” | 先完成采用，再启动下一章任务 | 续写以刚采用的内容为依据 |

意图和对象清楚时直接执行。存在多个候选稿、过时结果或“这个版本”无法唯一定位时，先定位对象；不根据含糊的“继续”自动采用某份草稿。

仅说“继续”时，根据当前状态处理：正在讨论则继续讨论；任务已暂停则继续该任务；当前章已采用且下一章目标明确则继续下一章；有待采用稿时指出该稿并给出“继续修改”与“采用并续写”操作。

在本草案推荐的逐章采用节奏下，有待采用稿时再次要求“写下一章”，先展示当前待采用的章节和版本，提供修改、另写当前章或采用并续写的操作。写后续章节以当前章已经采用为前提；连续推进多章未采用稿属于第 2 节的其他创作节奏，暂不纳入本首版范围。同一章的写作任务仍在运行时，重复发出的同一请求返回该任务的进度，不能因此另起一轮生成；明确要求另写一版时才按新任务处理。

用户请求查资料、解释或讨论时，不应顺带启动新的写章任务。用户提出复合但明确的任务时，例如“采用这一章，再写下一章”，可以连续完成。

## 6. 一章的交付与采用

### 6.1 执行中的体验

任务开始时展示目标章节、执行范围和预计消耗，消耗沿用平台的统一展示口径。价格计算和购买流程不属于本文件范围。

开始时同时说明离开页面后的执行规则，默认行为见第 8.1 节；用户可主动暂停任务。

用户能看到“准备本章”“创作中”“检查中”“根据检查修改”等进度，可暂停或补充指令。

首版建议：一次写章任务包含一次初稿生成，以及检查需要时至多一次自动修订；均应在开始时展示的消耗范围内。检查后仍有必须处理的问题，或继续执行会超出范围时，保留结果并等待用户下一条指令。

用户在执行中改变方向时，Agent 回报已收到的变更；从适当位置继续或停止并重新规划。无法应用到本次任务的要求必须说明，不能显示“已修改”却仍交付旧方向的结果。

### 6.2 结果需要包含的信息

| 内容 | 用户据此判断什么 |
| --- | --- |
| 当前章节与版本、草稿状态 | 正在看哪一份内容，是否已经采用 |
| 简短的章节摘要 | 这一章发生了什么 |
| 关键变化与前后对比 | 人物知道、获得、失去或改变了什么 |
| 情节与伏笔变化 | 哪些线被推进、新埋、部分兑现或完全兑现 |
| 问题与依据 | 哪些需要处理，哪些是建议或待核对判断 |
| 对应原文入口 | 立即查看支持某项判断的文字 |
| 本次执行情况 | 哪些工作已完成、是否还有未完成步骤，以及实际消耗 |

优先操作为“修改”和“采用并继续”；同时提供单独“采用”、查看正文和查看历史版本。用户无须逐条点击确认每个普通事件，采用时一并确认该版本呈现的变化。

操作名称随状态变化：手动编辑后需要核对的稿件提供“检查”和“检查并采用”；后者在检查通过后继续用户已请求的采用操作，有必须处理的问题时停在结果页。

新增设定、角色死亡、重大关系变化或与计划明显不同的结局，需要在采用区域突出展示，避免隐藏在长摘要里。

如果结构摘要或检查判断与正文不符，用户可以说“正文保持，纠正这条记录”，或对具体问题要求复核。例如，正文只写师父昏倒，结构记录却标成死亡时，Agent 应核对原文并修正候选记录。修正后展示变化、使受影响的检查结果过时，并重新检查；正文可以保持原样。最新已采用章的此类修正按第 8.2 节先形成候选新版本，再由用户采用。

### 6.3 哪些结果可以采用

- 正文和结构记录准备完成、当前版本的检查已结束且没有必须处理项，才进入“待采用”。仍有必须处理项时标记为“需要修改”，展示问题和依据。
- 必须处理的问题依据用户认可的规则或内容一致性要求产生；用户可修改正文、纠正候选结构记录、要求复核判断，或明确调整本章目标，再重新检查。复核需展示依据，已证实的内容不一致仍需处理。
- 建议和主观判断可由用户保留；不能仅因 Agent 不喜欢某种写法就禁止采用。
- 采用操作同时推进正文、相关设定和结构记录。出现保存失败时，应显示“采用未完成”，并保留可恢复的结果；其他视图不能呈现一半已生效的正式进度，重试不得重复新增章节或事件。
- 连续点击采用、刷新页面或从另一页面重复采用同一版本，应回到同一个采用结果。
- 查看旧结果时，如果正式作品依据已改变，提示“基于较早版本，需要重新核对”，完成核对前不能直接覆盖新进度。

## 7. 需要让用户看清的状态

任务进度与作品内容分开呈现。一项生成任务结束，只表示交付了结果，不代表用户已经采用。

### 7.1 任务进度

| 状态 | 含义 | 用户下一步 |
| --- | --- | --- |
| 正在处理 | Agent 正在执行当前范围内的工作 | 等待、补充要求或暂停 |
| 等待你的决定 | 存在方向分歧、范围变化或需要追加工作 | 选择方向或下达新指令 |
| 已暂停 | 用户主动暂停，已完成部分保留 | 继续任务或结束本次任务 |
| 已结束 | 用户主动结束本次任务，已得到的草稿保留 | 查看结果或发起新任务 |
| 未完成 | 发生失败，仍有步骤未完成 | 查看已有结果、重试未完成步骤 |
| 本次任务完成 | 当前范围内的交付已完成 | 查看结果；章节结果可能仍待采用 |

“等待你的决定”表示当前任务尚有分歧需要解决；交付待采用稿时，写章任务可以已经完成，采用由用户下一条指令触发。

### 7.2 章节内容

未完成草稿 → 待检查 → 检查中 → 待采用 → 已采用。

检查发现必须处理项时，从检查中转为“需要修改”；用户调整正文或本章目标后重新进入待检查，检查通过后才进入待采用。

- 修改待采用稿时形成新的当前草稿，旧稿进入历史版本；新稿检查完成后再进入待采用。
- 用户手动编辑并保存后，当前未采用稿进入“待检查”，原来的检查结果显示为过时。选择“检查”或“检查并采用”后才进入检查中，避免把保存内容误显示为正在执行检查。
- 仅纠正候选结构记录或检查判断时，也要更新候选结果并使相关检查过时；复核完成后再判断是否进入待采用，采用始终针对更新后的完整结果。
- 用户明确丢弃草稿后，它退出当前待办，保留在可查看的历史结果中，不影响正式作品。
- 当前任务失败或停止后，已得到的正文仍可查看。正文不完整时为未完成草稿；正文完整而核对尚未完成时为待检查，并显示上次检查未完成的原因。

### 7.3 故事安排与问题

- 备选想法：还未选定的创作可能性。
- 已计划：未来希望发生的事件，不能当作正文已经发生的事实。
- 待采用变化：当前草稿描述的变化，尚未成为正式作品进度。
- 已发生：已采用正文及对应记录支持的变化。
- 问题已安排：有明确的后续处理计划，问题本身还没有解决。
- 已改期：用户更新了预期处理时间，按新计划继续跟踪；伏笔仍未兑现。
- 已放弃：用户选择不再兑现，保留该决定和历史；不能显示为已兑现。
- 问题已解决：已采用正文满足该问题的处理目标。伏笔完全收束显示已兑现，部分收束显示部分兑现并继续跟踪剩余承诺；明确退场等作者决定按其具体处理方式展示。

## 8. 返回作品、修改与异常处理

### 8.1 返回与续写

重新打开作品时，显示最新已采用章节、待采用稿、未完成任务、当前优先问题与下一章计划。用户不用重新讲述已保存的设定和偏好。

已经执行完的任务不会因刷新或重新进入而自动再次生成。用户选择继续时，使用其已保存进度及当前适用的作品版本。

首版建议：关闭或离开页面不等于暂停。只要运行服务仍可用，任务就在已展示的执行次数和消耗范围内继续，遇到需要作者决定的问题时停下。用户回来后连接同一任务，显示真实进度或已经生成的结果，不重复启动任务；希望停止推进时使用“暂停”或“结束本次任务”。

如果运行服务或连接中断导致任务无法继续，应保留已完成步骤并显示未完成原因。返回页面先恢复查看状态，用户要求继续或重试后，再从适用的未完成步骤执行；页面重开本身不触发新的生成。

### 8.2 修改范围

首版建议支持当前未采用稿，以及最新已采用章的修改。修改最新已采用章时，先形成候选新版本，用户采用后再替换正式版本；旧版本仍可查看。

如果下一章已有草稿，前一章的新版本被采用后，下一章草稿标记为需要重新核对。用户可以要求按新事实修改该稿，完成检查后再采用。

修改更早且已有多章后续正文的章节时，首版交付影响分析和修改建议，说明当前支持的范围。跨多章正式返修属于后续独立流程；不能静默改掉整本书或声称已完成返修。

用户选定局部修改范围时，结果展示该范围内的改动；如必须扩大范围，先解释影响并提供修改建议。

### 8.3 异常分支

| 情况 | 用户看到的结果 | 恢复方式 |
| --- | --- | --- |
| 正文已生成，后续检查失败 | 保留正文，标记检查未完成 | 重试后续检查；不自动重新写正文 |
| 生成中断，仅有部分正文 | 标记未完成草稿，并保留片段 | 用户选择继续完成或重新生成 |
| 用户暂停或结束任务 | 当前任务停止推进，已完成内容保留 | 暂停可继续；结束后可另发任务 |
| 生成中关闭页面 | 服务可用时在既定范围内继续，必要决定处停下 | 返回查看同一任务；若任务因服务中断而未完成，按保留进度重试 |
| 自动修订后仍有必须处理项 | 章节标记为需要修改，展示问题、证据和已有版本 | 用户修改目标、提出具体修订或结束任务 |
| 结构记录或检查判断有误 | 展示原文依据和待复核项，保留正文 | 纠正候选记录或复核判断，更新受影响检查后再判断采用条件 |
| 采用保存失败 | 显示采用未完成，保留同一份结果 | 重试同一次采用，避免重复章节或记录 |
| “采用并继续”中采用成功、下一章生成失败 | 分别显示前章已采用、下一章任务未完成 | 只恢复下一章任务，不重复采用前章 |
| 另一页面已更改正式版本 | 标记当前结果基于旧版本 | 先同步最新进度并核对当前稿 |
| 正文被编辑后引用失效 | 对应结构项显示需要重新定位或核对 | 重新核对后提供有效正文入口 |
| 用户要求超出本次范围 | 说明需要扩大的工作和消耗 | 用户明确扩大范围后继续 |

### 8.4 导出已采用正文

作者从章节列表或对话发起导出，选择全部已采用章节或连续的章号范围。生成文件前展示将包含的章节及正式版本，同时指出范围内尚未采用的章节；未采用稿不纳入本次导出。范围内没有已采用正文时说明原因，作者可以调整范围或先处理草稿。

导出生成按章号排序的基础文本文件。文件使用此次选定的版本集合；导出期间发生的新采用不会让同一份文件混入两个时点的版本，作者可以随后重新导出。导出是读取作品的操作，不触发写章或采用。

## 9. 一个贯穿示例

示例用于检查交互和状态，不是要为项目新增一部演示小说。

1. 用户：“写一本玄幻悬疑，主角寻找失踪的母亲，先给我两个开篇方向。”
2. Agent：整理用户设定，给出两种开篇方案及区别，均保持为建议。
3. 用户：“第二个，先不要揭开信的内容，直接写第一章。”
4. Agent：展示选定目标和本次范围，生成并检查第一章，交付待采用稿；“信的内容”仍未成为已发生的揭晓事件。
5. 用户：“主角答应得太快了，加一轮试探，保持结尾不变。”
6. Agent：形成修订稿，说明改动，更新本章结构摘要，完成检查后展示新的待采用版本。
7. 用户：“采用并继续下一章。”
8. Agent：采用修订稿后开始第二章；第二章基于新增的试探及人物获得的信息，不能继续沿用已被替换的初稿事实。
9. 用户在第二章结果出现后关闭页面；回来时看到第 1 章已采用、第 2 章待采用，系统没有再次生成第 2 章。
10. 用户要求把信的部分线索安排进第 3 章；系统显示已安排，等相关正文实际写出并采用后才显示部分兑现。

## 10. 首版验收场景

以下是实现后需要实际验证的用户行为，本轮没有声称这些功能已经通过验收。

- 用户从新想法创建作品，通过对话完成首章生成、一次修改、采用和下一章创作。
- “只讨论一种可能性”不会改变正式设定；“采用这个方案”会清楚反映所采用的具体内容。
- 用户能只读摘要和结构变化说明本章发生了什么，也能从关键变化跳到正确原文。
- 未采用的正文和结构变化不会出现在默认的正式故事概览中；查看草稿时可以明确切换到该稿的候选变化。
- 修改后的内容进入后续创作依据，被替换的初稿事实不会继续被当成正式事实。
- 把问题加入后续计划后显示已安排；仅在满足对应处理条件后显示具体的完成状态。
- 刷新、返回和重复点击采用不造成重复生成、重复章节或重复结构变化。
- 当前章尚未采用时，“写下一章”不会越过该稿推进正式进度；同一写章请求的重试连接原任务，明确另写一版才新建任务。
- 正文已完成但检查失败时，用户仍能看到正文，并从未完成步骤继续。
- 检查执行成功但发现必须处理项时，章节显示需要修改；不因任务执行结束而显示为可采用。
- 正文正确但结构记录误读时，用户可保留正文、纠正候选记录并重新检查；采用后正文与结构视图一致。
- 生成中离开页面，服务可用时任务在既定范围内继续；返回连接同一任务，能看见结果或真实未完成状态，不重复生成或自动采用。
- 最新已采用章被修改后，依赖它的下一章草稿会要求重新核对。
- 连续创作 3～5 章，检查人工干预是否准确影响后续正文、人物状态和伏笔记录。
- 用户能够导出选定范围内的已采用正文，导出版本与界面显示一致。
- 导出明确列出实际包含的章节和版本；未采用稿不会被混入，范围内没有已采用正文时能调整范围；导出期间采用新版本不改变已选定的版本集合。

## 11. 后续细化的顺序

先评审本文件中的默认创作节奏与首版范围，再明确用户操作对应的界面结果和状态变化。随后将这些行为映射为任务编排、工具边界、小说存储和服务端 / Web 入口，选择适合的框架并制定实现计划。

无需重新确认已经明确的对话式入口和 Agent 自主选择工具需求；后续反馈应集中在尚未定案的具体默认行为和范围。
