# 跨多章返修：改早章之后，定位受影响段落并给修订建议（差距第 5 项下半场）

2026-09-18 / 分支 `cross-chapter-revision`（base `master`，不栈）/ 基线 `7df8960`

## 目标

差距盘点第 5 项的下半场。上半场（连续创作，第 33 节）解决「一次多写几章」，这一批解决反方向的问题：**改了前面的章之后，后面几十章怎么办**。此前只把未采用的后续草稿标 `stale`，已采用的章一概不管。

真正的缺口比盘点里写的更硬：`draft-revisions.ts` 的 `source()` 直接挡死早章返修，报错文案写的就是「更早章节需先分析后续影响，不能直接返修」。所以这一批先做那份分析，再用它解锁早章。

## 两个通道，分工不同

| | 判据 | 谁判 | 成本 |
| --- | --- | --- | --- |
| **硬矛盾** | 结构事实对不上：悬空兑现、生死状态变了人还在、状态/关系链接在被改掉的值上 | 代码读事件流 | 0 |
| **受影响段落** | 正文里哪几句依赖了被改掉的事实 | 模型读那一章正文 | 一次调用／章 |

代码通道免费且确定，进页面就在；模型通道**一次只查一章、由作者点**，不在服务端起长任务，也不自动全书扫。

## 范围决策

- **不靠情节线扩散。** 改一章的事件叙述，不足以指认第 40 章受影响 —— 同一条主线上的章动辄几十个，全圈进来等于没圈，作者会关掉整个功能。代码只圈**有编号可查的关联**（同一条伏笔、同一个人物的同一字段、同一对关系），外加**紧接的下一章**（相邻关系，不是阈值）。圈不到的由作者自己点查任意后续章，`latest` 就是那条线索。
- **产物是建议，不是改稿。** 每条给引文、为什么、怎么改；落笔仍走那一章的结果页。与「逐章采用」「模型产出先 proposed」同一条原则。
- **未处理的硬矛盾只挡连写，不挡单章手写**（用户 2026-09-18 拍板）。连写是批量，会在错的基准上一口气堆好几章；单章手写作者本来就盯着结果页，挡住只会碍事。
- **一个受影响章只有一条记录**，同一章被多次修订牵连时合并。作者面对的问题始终是「第 K 章现在要不要改」，不是「它欠了几笔账」。合并态算一个指纹，「已处理」记在指纹上 —— 再来一次修订指纹就变，这一章自动重新亮起。
- **正文改了、结构没变也算一次修订**：重写一场戏而不改声明是常事，后面引用那场戏细节的段落照样会失效。
- 没有引入任何新阈值，`rules.yaml` 未改。定位的 `maxTokens` 与 `steps.ts` 同类，是管线常量。

## 实现

- `src/revise/impact.ts`：`diffDeclarations`（按对象编号配对，不按位置 —— 重写一章会把条目重排）、`impactedChapters`（conflict / review 两级）。纯函数。
- `src/revise/locate.ts`：模型通道的提示、schema 与解析。纪律照搬 `gate/semantics-channel.ts`：引文必须逐字在正文里，否则丢弃并说清丢了几条；输出不成形就降级为「本轮没查成」。
- `src/revise/store.ts`：`revision-impact.json`（按受影响章合并的记录 + `latest`）。
- `src/revise/service.ts`：`view / preview / record / locate / resolve / assertNoConflicts`。
- 接线：`state.ts` 采用早章时取改动前的声明（必须在 `supersedeChapter` 之前）并落清单；连写 `assertCanStart` 加返修闸门；`draft-revisions.ts` 放开早章；`api.ts` 四个端点 + overview 计数。
- `event-stream.ts` 提取 `declarationOf`（原在 `import/inference.ts` 私有），两处复用。
- Web：新页 `Revision.tsx`（`/revision`，有待办才出现在导航）、`Drafts.tsx` 采用前预览、`api.ts`。
