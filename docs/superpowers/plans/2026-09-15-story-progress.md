# 故事安排、问题进度与伏笔生命周期实施计划

> **执行方式：** 当前代理使用 `superpowers:executing-plans`、TDD 和完成前验证实施并自审，不启动独立 Agent。沿用已授权用户流程 §7.3、§9–10 及总计划 Chunk 1/3/5，不重复请求设计批准。

**Goal:** 作者能区分已安排、已改期、已放弃、部分兑现、正文已解决及作者确认退场；已确认的未来伏笔进入正文后沿用原编号，直到真正采用兑现内容才结束跟踪。

**Architecture:** 事件流和已确认节拍仍为唯一来源。处理进度作为可重建读模型，计划动作由一个业务入口校验和事务保存，按钮与对话共用；C5 只把有正文依据的规划埋设链接到既有编号。保持未完全兑现的伏笔在现有 `open` 债务集合中，用户界面单独展示部分兑现及剩余安排。

**Tech Stack:** TypeScript、ProjectSession、EventStream、现有文件事务、React、Vitest、Playwright。

## 设计与边界

- 不另存一份会与事件流分歧的“已解决”开关。进度由正式伏笔、已确认章节安排、作者改期/放弃记录及正文中的实际推进/出场重建；候选稿和 P4 规划不能充当已发生证据。
- 伏笔显示正文进度及安排：未来规划、未兑现、部分兑现、已兑现、已放弃；安排字段列出具体章节/完整或部分目标及改期历史。完全兑现才停止债务跟踪，放弃保留原因。
- 情节线/人物安排也核对正式推进/出场；正文没有对应记录时保留未完成。作者确认退场明确显示为作者决定，不伪装成正文补写或死亡。
- 统一动作服务验证对象、章号、已确认计划、伏笔权重与可操作状态；拒绝借另一条告警修改无关对象或已采用章节。相同动作重试无重复事件；组合保存失败整组回滚。
- 改期明确修改预期兑现期限，展示与实际章节安排的区别；放弃时清除未来章节对该伏笔的回收安排并重算预算，避免后续开写因已放弃引用阻塞。保留过去计划和正文历史。
- 页面改期必须输入新章号，放弃可填写原因；操作后立即刷新进度。当前只传旧期限的改期按钮及不随同章计划变更刷新的提示页均需验证和修复。
- C5 可提供 `planned_foreshadow_id`，也可用唯一且完全相同的既有规划标签关联；歧义或非法引用必须可见失败。新伏笔仍分配新 ID。确认规划的意图与期限进入本章相关上下文，不混入“已埋设”索引。
- 采用前规划保持原态，采用后同一 ID 成为真正埋设并有原文入口；重写最新章使该埋设作废时，原作者规划仍保留。作者改期/放弃记录不能被后来 C5 埋设静默抹掉。
